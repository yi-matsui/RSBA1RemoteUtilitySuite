# プロトコル仕様

> ステータス: 拡張モードの制御チャネル（UDP 50001、Phase 3）と CI-V / オーディオのデータチャネル
> （UDP 50002 / 50003、Phase 4）を実装済み。
> 実装: `src/common/ctl_proto.[ch]`、`dch.[ch]`、`civ_link.[ch]`、`audio_link.[ch]`、`jbuf.[ch]`、
> `src/server/ctl_server.[ch]`、`src/client/ctl_client.[ch]`。

## 1. 概要

- 純正 RS-BA1 Remote Utility の UDP ポート構成（50001 / 50002 / 50003）を基礎とする。
- 両端が本スイートの場合は「拡張モード」として IPv6 ネイティブ、相互認証、改ざん・リプレイ検知、
  Opus 音声、動的ジッター制御を使用する。本書の制御チャネル仕様は拡張モードのものである。
- 片側が純正 Remote Utility の場合の「互換モード」（SPEC の「必要に応じて」保持する下位互換）は未実装で、今後の拡張課題とする。

## 2. ポート割り当て

| ポート | 用途 | 拡張モード |
|---|---|---|
| 50001/udp | 制御（認証・Keepalive・セッション管理） | 本書 §3〜§7 |
| 50002/udp | CI-V シリアル透過 | 本書 §8〜§9 |
| 50003/udp | オーディオ | 本書 §8・§10 |

サーバは 3 ポートすべてを同じデュアルスタック待受アドレスで開く（`--port N` で N / N+1 / N+2）。
クライアントは各チャネルにエフェメラルポートの別ソケットを使う。

## 3. 共通パケット制約

- UDP ペイロード長は IPv6 最小 MTU（1280）から IPv6 ヘッダ（40）・UDP ヘッダ（8）を引いた **1232 バイト以下**。
  制御パケットは最大 112 バイト（HELLO）。
- 多バイト整数は**ビッグエンディアン**。
- 受信側は §4 の長さ規則に一致しないパケットを黙って破棄する（応答しない）。

## 4. パケットフォーマット

### 4.1 共通ヘッダ（16 バイト）

| オフセット | サイズ | フィールド | 説明 |
|---|---|---|---|
| 0 | 4 | magic | `'R' 'S' 'B' 'A'` |
| 4 | 1 | version | `1` |
| 5 | 1 | type | §4.3 |
| 6 | 2 | payload_len | ペイロード長。種別ごとに固定値（§4.3）で、不一致は破棄 |
| 8 | 4 | session_id | セッション ID。ハンドシェイク中（HELLO〜AUTH, AUTH_FAIL）は 0 |
| 12 | 4 | seq | 方向別シーケンス番号。タグ付きパケットは 1 から開始、それ以外は 0 |
| 16 | n | payload | |
| 16+n | 16 | tag | タグ付き種別のみ。HMAC-SHA256(方向別セッション鍵, ヘッダ‖ペイロード) の先頭 16 バイト |

パケット全長 = 16 + payload_len (+ 16)。

### 4.2 鍵とタグ

| 名前 | 定義 | 送信されるか |
|---|---|---|
| `K`（パスワード鍵） | PBKDF2-HMAC-SHA256(password, salt, iterations, 32) | しない |
| `cn` / `sn` | クライアント / サーバのノンス（各 16 バイト、OS 乱数） | する |
| client_proof | HMAC(K, `"RSBA1 client"` ‖ cn ‖ sn ‖ username) | する（AUTH） |
| server_proof | HMAC(K, `"RSBA1 server"` ‖ sn ‖ cn ‖ session_id) | する（AUTH_OK） |
| `K_c2s` | HMAC(K, `"RSBA1 c2s"` ‖ cn ‖ sn ‖ session_id) | しない |
| `K_s2c` | HMAC(K, `"RSBA1 s2c"` ‖ cn ‖ sn ‖ session_id) | しない |

- **セッショントークンの扱い**: セッションの秘密は `K_c2s` / `K_s2c` であり、ネットワークに一度も流れない。
  `session_id` は公開の識別子にすぎず、これだけではパケットを偽造できない。
  パスワード・`K` も送信されない（証明値のみ送信）。
- 方向別の鍵を使うため、相手から受け取ったパケットを送り返す反射攻撃は成立しない。
- 秘密値はセッション終了時・オブジェクト破棄時に消去する（`rs_crypto_wipe`）。
- 本フェーズの制御パケットは**完全性・真正性**を保護するが、ペイロードの暗号化は行わない
  （制御ペイロードに秘密情報を含まないため）。CI-V / オーディオのペイロードは §8 のとおり暗号化する。

### 4.3 種別とペイロード

| type | 名前 | 方向 | タグ | payload_len | ペイロード |
|---|---|---|---|---|---|
| 1 | HELLO | C→S | なし | 96 | cn(16) ‖ user_len(1) ‖ username(user_len ≤ 32) ‖ 0 埋め |
| 2 | CHALLENGE | S→C | なし | 52 | sn(16) ‖ cn(16, エコー) ‖ salt(16) ‖ iterations(u32) |
| 3 | AUTH | C→S | なし | 64 | cn(16) ‖ sn(16) ‖ client_proof(32) |
| 4 | AUTH_OK | S→C | `K_s2c` | 40 | server_proof(32) ‖ keepalive_interval_ms(u32) ‖ keepalive_timeout_ms(u32) |
| 5 | AUTH_FAIL | S→C | なし | 1 | reason: 1 = 資格情報不一致, 2 = チャレンジ期限切れ・不整合 |
| 6 | PING | C→S | `K_c2s` | 8 | 送信時刻（クライアントのミリ秒時計, u64） |
| 7 | PONG | S→C | `K_s2c` | 8 | PING の値をそのまま返す（RTT 計測用） |
| 8 | DISCONNECT | 双方向 | 方向別 | 1 | reason: 0 = normal, 1 = shutdown, 2 = replaced, 3 = timeout |

- HELLO は増幅攻撃対策として CHALLENGE（52）以上の長さに固定する（送信元を詐称した要求で、
  第三者へより大きな応答を送らせない）。この関係はコンパイル時に検査している。
- AUTH_FAIL はユーザ名不一致とパスワード不一致を区別しない。

## 5. 認証・セキュリティ

### 5.1 チャレンジ・レスポンス認証（相互認証）

1. クライアントは cn を生成し HELLO を送る。
2. サーバは sn を生成し、(送信元アドレス, cn, sn) を**保留チャレンジ**として記録して CHALLENGE を返す。
   - 未知のユーザ名に対しても、サーバ秘密値から決定的に作った**偽ソルト**で CHALLENGE を返す
     （応答の有無・ソルトの変化からユーザ名の存在を推測させない）。
   - 保留チャレンジは最大 16 件。満杯時は最古を破棄。有効期間 `challenge_timeout_ms`（5 秒）。
3. クライアントは salt と iterations から `K` を導出し（ソルトごとにキャッシュ）、client_proof を AUTH で送る。
   - iterations が上限（既定 1,000,000）を超える CHALLENGE は無視する（悪意あるサーバによる CPU 消費攻撃対策）。
4. サーバは保留チャレンジを照合して**消費**（1 回限り）し、client_proof を定数時間比較で検証する。
   - 一致: session_id を乱数で発行し、セッション鍵を導出して AUTH_OK を返す。
   - 不一致: AUTH_FAIL(1) を返し、失敗を §5.4 に記録する。
   - 保留チャレンジなし・期限切れ: AUTH_FAIL(2)。失敗回数には数えない（再送・遅延の可能性があるため）。
5. クライアントは AUTH_OK のタグを `K_s2c` で検証し、さらに server_proof を検証する。
   - タグ不一致: 偽造の可能性があるため無視（ハンドシェイクタイムアウトで再試行）。
   - server_proof 不一致: なりすましサーバとみなし切断（`server_proof`）。再接続しない。

### 5.2 セッション（1 本のみ）

- サーバが同時に保持するセッションは 1 本。別のクライアントが認証に成功した場合、既存セッションは
  `replaced` として終了し（PTT 解除・DISCONNECT(2) 送信）、新しいセッションに置き換える。
- 置き換えられたクライアントは自動再接続しない（2 台による奪い合いを防ぐ）。
- 正当なタグを持つパケットの送信元アドレスが変わった場合、サーバはピアアドレスを更新する
  （NAT の再割り当て・回線切り替えへの追従）。

### 5.3 改ざん・リプレイ検知

受信側は以下の順に検査し、いずれかに該当するパケットを破棄する（応答しない）。

| 順 | 検査 | 破棄理由（サーバ統計） |
|---|---|---|
| 1 | 送信元が遮断中 | `rx_banned` |
| 2 | ヘッダ形式（magic / version / 種別 / 長さ） | `rx_malformed` |
| 3 | セッションあり・session_id 一致 | `rx_unknown_session` |
| 4 | seq がリプレイウィンドウ内で未受理 | `rx_replay` |
| 5 | タグ一致（定数時間比較） | `rx_bad_tag` |

- **リプレイウィンドウ**: 方向ごとに受理済み最大 seq と 64 ビットのビットマップを持つ（RFC 4303 方式）。
  最大値より 64 以上古い seq と受理済みの seq を拒否する。UDP の順序入れ替わりは 64 パケットまで許容する。
  ウィンドウはタグ検証に成功した後にのみ更新する。
- **ハンドシェイクのリプレイ**: AUTH は sn（サーバが毎回生成し 1 回で消費）に束縛されるため、
  過去の AUTH を再送してもセッションは確立しない。
- **鮮度**: セッション鍵は毎回のノンスから導出されるため、過去のセッションのパケットは現在の鍵で検証に失敗する。
  時刻同期を前提としたタイムスタンプ検証は行わない（PING のタイムスタンプは RTT 計測専用）。

### 5.4 連続認証失敗時の IP 遮断

| 項目 | 既定値 | 内容 |
|---|---|---|
| 単位 | 送信元 IP アドレス | ポートは区別しない（IPv4 は mapped アドレスとして扱う） |
| `max_failures` | 5 | `failure_window_ms`（5 分）内の失敗回数がこれに達したら遮断 |
| `ban_ms` | 900000（15 分） | 遮断中はその IP からの全パケットを無応答で破棄 |
| テーブル | 256 件 | 満杯時は遮断中でない最古のエントリを再利用 |

- 失敗として数えるのは client_proof の不一致（未知ユーザを含む）のみ。形式不正・タグ不一致は送信元詐称が
  容易なため数えない（正規ユーザの IP を遮断させる攻撃を防ぐ）。
- 認証成功でその IP の失敗履歴を消去する。
- クライアントは認証失敗時に自動再接続しない（誤設定で自分の IP を遮断させないため）。

## 6. 通信シーケンス

### 6.1 接続確立

```text
client_bridge                                       server_bridge
 IDLE                                                WAITING
   |  HELLO (cn, username)                     --->  |  保留チャレンジ記録
 HELLO_SENT                                          |
   |  <---  CHALLENGE (sn, cn, salt, iterations)     |
   |  K = PBKDF2(password, salt)                     |
   |  AUTH (cn, sn, client_proof)              --->  |  照合・消費・検証
 AUTH_SENT                                           |  session_id 発行、K_c2s / K_s2c 導出
   |  <---  AUTH_OK [K_s2c] (server_proof, keepalive)|
   |  タグ・server_proof 検証                        ACTIVE
 CONNECTED
```

### 6.2 Keepalive

```text
   |  PING [K_c2s] seq=n (t)                   --->  |  last_rx 更新
   |  <---  PONG [K_s2c] seq=m (t)                   |
   |  RTT = now - t                                  |
```

- クライアントは `keepalive_interval_ms`（サーバ通知値、既定 1000）ごとに PING を送る。
- サーバは最後の正当な受信から `keepalive_timeout_ms`（既定 5000）経過でセッションを破棄する。
- クライアントは最後の正当な受信（PONG）から同じ時間経過で切断とみなす。
- サーバ通知値は 100〜60000 ms に制限し、タイムアウトは周期の 2 倍以上に補正する。

### 6.3 正常切断

```text
   |  DISCONNECT [K_c2s] (0 = normal)          --->  |  PTT 強制解除 → セッション破棄 → WAITING
 IDLE（自動再接続しない）
```

### 6.4 異常切断（Keepalive 途絶）

サーバは `ctl_server_tick` で途絶を検知し、以下を順に行って待機状態へ遷移する。

1. IC-9100 へ PTT 強制解除（CI-V `FE FE 7C E0 1C 00 00 FD`）を発行（`ptt_release` フック）
2. DISCONNECT(3 = timeout) を最後のピアアドレスへ送信（届けば即時、届かなくてもクライアント側で途絶検知）
3. セッション鍵の消去・リプレイウィンドウ初期化
4. `session_end` フックを呼び、WAITING へ遷移

クライアントは途絶検知後 `reconnect_interval_ms`（3 秒）待って HELLO から再接続する。

### 6.5 サーバ終了

`ctl_server_shutdown` / `ctl_server_destroy`（Ctrl+C 時）で、セッションがあれば PTT 強制解除のうえ
DISCONNECT(1 = shutdown) を送る。クライアントは自動再接続を試み続ける。

## 7. セッション状態遷移

### 7.1 サーバ

| 現在状態 | イベント | 次状態 | アクション |
|---|---|---|---|
| WAITING | HELLO | WAITING | 保留チャレンジ記録、CHALLENGE 送信 |
| WAITING | AUTH（証明一致） | ACTIVE | session_id 発行、AUTH_OK 送信、`session_start` |
| WAITING | AUTH（証明不一致） | WAITING | AUTH_FAIL(1)、失敗記録（閾値で IP 遮断） |
| ACTIVE | PING（検査通過） | ACTIVE | PONG 送信、last_rx 更新 |
| ACTIVE | DISCONNECT（検査通過） | WAITING | PTT 解除、鍵消去、`session_end(client_disconnect)` |
| ACTIVE | 受信途絶 ≥ keepalive_timeout | WAITING | PTT 解除、DISCONNECT(3)、鍵消去、`session_end(timeout)` |
| ACTIVE | 別クライアントの AUTH（証明一致） | ACTIVE（新） | 旧: PTT 解除、DISCONNECT(2)、`session_end(replaced)` → 新セッション開始 |
| ACTIVE | shutdown / destroy | WAITING | PTT 解除、DISCONNECT(1)、`session_end(shutdown)` |
| 任意 | 検査不合格パケット | 変化なし | 破棄、統計加算 |

### 7.2 クライアント

| 現在状態 | イベント | 次状態 | 終了理由 / 自動再接続 |
|---|---|---|---|
| IDLE | `ctl_client_connect` / 再接続時刻到達 | HELLO_SENT | |
| HELLO_SENT | CHALLENGE（cn 一致） | AUTH_SENT | |
| AUTH_SENT | AUTH_OK（タグ・server_proof 一致） | CONNECTED | `connected` フック |
| AUTH_SENT | AUTH_OK（server_proof 不一致） | IDLE | `server_proof` / しない |
| HELLO_SENT / AUTH_SENT | AUTH_FAIL(1) | IDLE | `auth_failed` / しない |
| HELLO_SENT / AUTH_SENT | AUTH_FAIL(2) / 応答なし ≥ handshake_timeout | IDLE | `handshake_timeout` / する |
| CONNECTED | 受信途絶 ≥ keepalive_timeout | IDLE | `timeout` / する |
| CONNECTED | DISCONNECT(2 = replaced) | IDLE | `replaced` / しない |
| CONNECTED | DISCONNECT（その他） | IDLE | `server` / する |
| 任意 | `ctl_client_disconnect` | IDLE | `user` / しない（CONNECTED なら DISCONNECT(0) 送信） |

## 8. データチャネル共通（UDP 50002 / 50003）

### 8.1 パケット形式

制御チャネルと同じ 16 バイトのヘッダを使い、ペイロードを暗号化してタグを付ける（Encrypt-then-MAC）。

| オフセット | サイズ | フィールド | 説明 |
|---|---|---|---|
| 0 | 4 | magic | `'R' 'S' 'B' 'A'` |
| 4 | 1 | version | `1` |
| 5 | 1 | type | `0x10` BIND / `0x11` CIV / `0x12` AUDIO |
| 6 | 2 | payload_len | 暗号文の長さ（0〜1200） |
| 8 | 4 | session_id | 制御チャネルのセッション ID |
| 12 | 4 | seq | チャネル・方向ごとのシーケンス番号（1 から） |
| 16 | n | ciphertext | ChaCha20(enc 鍵, nonce, counter = 1) でペイロードを暗号化したもの |
| 16+n | 16 | tag | HMAC-SHA256(mac 鍵, ヘッダ ‖ 暗号文) の先頭 16 バイト |

- 最大ペイロード 1200 バイト（16 + 1200 + 16 = 1232 = IPv6 最小 MTU 内の最大 UDP ペイロード）。
- nonce（12 バイト）= `00 00 00 00` ‖ seq（BE 4 バイト）‖ `00 00 00 00`。鍵がチャネル・方向ごとに
  異なり、seq は鍵ごとに単調増加するため (鍵, nonce) は再利用されない。seq が 2^32 − 1 に達したら送信を止める。

### 8.2 鍵導出

制御チャネルのセッション鍵（§4.2 の `K_c2s` / `K_s2c`、送信されない）から導出する。

| 鍵 | 定義 |
|---|---|
| enc（C→S, CI-V） | HMAC(`K_c2s`, `"RSBA1 civ enc"`) |
| mac（C→S, CI-V） | HMAC(`K_c2s`, `"RSBA1 civ mac"`) |
| enc / mac（S→C, CI-V） | 同上で `K_s2c` |
| enc / mac（オーディオ） | 同上でラベル `"RSBA1 audio enc"` / `"RSBA1 audio mac"` |

チャネルごとに鍵が異なるため、あるチャネルのパケットを別のチャネルへ流用しても受理されない。
制御チャネルのタグ鍵でデータパケットを偽造することもできない。

### 8.3 受信検査

形式（magic / version / type / 長さ）→ session_id → リプレイウィンドウ（§5.3 と同じ 64 パケット幅）→
タグ（定数時間比較）→ 復号 の順に検査し、不合格は応答せず破棄して統計に計上する
（`rx_malformed` / `rx_unknown_session` / `rx_replay` / `rx_bad_tag`）。
セッションがない間（制御チャネルが WAITING / IDLE）は鍵がないため、すべて破棄する。

### 8.4 アドレス登録（BIND）

- クライアントはセッション確立直後と、以後 1 秒ごとに、CI-V・オーディオ各ソケットから
  空ペイロードの BIND を送る（サーバへの送信元アドレス登録と NAT のマッピング維持）。
- サーバは**検査に合格した**パケット（BIND に限らない）の送信元を、そのチャネルの送信先として学習・更新する。
  送信先が未確定の間、サーバからのデータは送らない。
- クライアントはサーバの各ポート以外からのパケットを破棄する。

### 8.5 セッションとの連動

| 制御チャネルのイベント | データチャネル |
|---|---|
| セッション開始（サーバ `session_start` / クライアント `connected`） | 鍵を導出して有効化、seq・リプレイウィンドウ・ジッターバッファを初期化 |
| セッション終了（全理由） | 鍵を消去して無効化。サーバは先に PTT 強制解除を送出（§9.3） |

## 9. CI-V 透過中継（UDP 50002）

### 9.1 CI-V 定義

- IC-9100 CI-V アドレス: `0x7C` ／ コントローラアドレス: `0xE0`
- フレーム: `FE FE <宛先> <送信元> <コマンド/データ> FD`（データ部は FE / FD を含まない）
- PTT 強制解除: コマンド `1C 00 00` → `FE FE 7C E0 1C 00 00 FD`（`civ_build_ptt_off`）

### 9.2 中継動作

| 方向 | 処理 |
|---|---|
| シリアル → ネットワーク | ノンブロッキング読み込み → フレーム切り出し（`civ_framer`）→ 1 回の読み込みで完成したフレームを 1 パケットにまとめて送信（最大 1200 バイト） |
| ネットワーク → シリアル | §8.3 の検査 → ペイロードが完全なフレームの連続であること（各 5〜128 バイト、FE FE 始まり・FD 終わり）を確認 → シリアルへ書き込み（タイムアウト 200 ms） |

- フレームにならないバイト（雑音・途切れたフレーム・128 バイト超）は転送せず破棄して数える
  （`garbage_pending` は USB 監視の「不正バッファ蓄積」検知に使う。[usb_reset_architecture.md](usb_reset_architecture.md) §4）。
- フレーム単位で送るため、パケットの境界でフレームが分断されない。遅延はシリアルの読み込み周期
  （イベントループ 2 ms）程度。
- 認証済みでもフレーム列として不正なペイロードはシリアルへ書かない（`rejected_payload`）。

| シリアル設定 | 値 |
|---|---|
| 形式 | 8N1、フロー制御なし、既定 19200 bps |
| DTR / RTS | 常にネゲート（IC-9100 の USB SEND / キーイングに割り当てられていても送信状態にしない） |
| 読み込み | ノンブロッキング（Win: `ReadIntervalTimeout = MAXDWORD`、Linux: `O_NONBLOCK` + `VMIN = VTIME = 0`） |
| 書き込み | 上限 200 ms（Win: `WriteTotalTimeoutConstant`、Linux: `poll(POLLOUT)`） |

### 9.3 PTT 強制解除（フェイルセーフ）

サーバは次のいずれでも `FE FE 7C E0 1C 00 00 FD` を**シリアルポートへ直接**書き込む
（セッション状態・鍵に依存しない `civ_link_write_raw`）。

| 契機 | 経路 |
|---|---|
| CI-V ポートを開いた直後（起動時・再接続時） | `serial_try_open` |
| セッション終了（クライアント切断・Keepalive 途絶・置き換え・サーバ終了） | `ctl_server` の `ptt_release` フック |
| USB リセットの直前 | `usb_reset_now` |
| プロセス終了要求（Ctrl+C、SIGTERM、SIGHUP、Windows のコンソール閉鎖・ログオフ・シャットダウン） | 停止フラグ → `ctl_server_destroy`（シリアルを閉じる前に実行） |

強制終了（kill -9 等）・クラッシュでは送出できない。サーバ自体が落ちた場合に備え、
無線機側の送信タイムアウトタイマー（TOT）の併用を推奨する。クライアント側の異常終了は、
サーバが Keepalive 途絶（5 秒）で検知して送出する。

## 10. オーディオ伝送（UDP 50003）

### 10.1 形式

| 項目 | 値 |
|---|---|
| サンプリング周波数 / 量子化 / チャンネル | 48 kHz / 16 bit / モノラル（IC-9100 USB Audio CODEC 標準） |
| フレーム長 | **10 ms = 480 サンプル**（PCM 960 バイト） |
| コーデック | PCM16（L16、ビッグエンディアン）。Opus はコーデック ID を予約し、インタフェースのみ用意 |
| ジッターバッファ | 適応制御 20 〜 80 ms |

20 ms の PCM フレーム（1920 バイト）は 1 パケット（最大 1200 バイト）に収まらないため、10 ms の
サブフレームに分割して送る（パケットあたり 16 + 8 + 960 + 16 = 1000 バイト、毎秒 100 パケット、
約 800 kbps / 方向）。Opus を組み込む場合は 20 ms フレームを 1 パケットで送れる。

### 10.2 ペイロード（暗号化前）

| オフセット | サイズ | フィールド | 説明 |
|---|---|---|---|
| 0 | 1 | codec | `1` = PCM16 / `2` = Opus（予約） |
| 1 | 1 | channels | `1` |
| 2 | 2 | frame_samples | 480 |
| 4 | 4 | timestamp | 送信側のサンプル時計（フレームごとに +480、初期値は乱数でフレーム境界に揃える、周回可） |
| 8 | n | data | 符号化データ（PCM16 は 960 バイト） |

受信側は codec / channels / frame_samples が自分の設定と一致しないフレームを破棄する（`rejected_format`）。

### 10.3 送受信の流れ

```text
送信: デバイス録音 → 480 サンプルごとに符号化 → 封緘 → 送信
受信: 検査・復号 → 復号 → ジッターバッファ（timestamp で配置）
再生: デバイスの再生キューに空きがあるたび 10 ms ずつジッターバッファから取り出して書く
      （デバイスのクロックが再生タイミングの基準。セッションがなくても無音を書き続けデバイスを止めない）
```

### 10.4 適応型ジッターバッファ

| 処理 | 内容 |
|---|---|
| 格納 | timestamp からフレーム番号を求め、リングのスロットに格納（順序入れ替わり・重複・遅着を吸収）。容量は最大遅延の 2 倍 + 8 フレーム以上 |
| 揺らぎ推計 | transit = 到着時刻 − メディア時刻。直近 256 到着の transit の最大 − 最小をジッターとする |
| 目標遅延 | clamp(ジッター + 1 フレーム + 再生側の塊, 20, 80) ms。増加は即時、減少は 1 フレームあたり 0.25 ms |
| 再生側の塊 | デバイスが一度にまとめて空きを返すフレーム数の直近最大値 − 1 フレーム分（例: WinMM で 30 ms） |
| 再生開始 | 目標遅延分たまるまで無音を出力（BUFFERING） |
| 微調整 | 平滑化したバッファ量（1/64 の指数平滑）と瞬時値が、目標 + 半フレーム超なら速め、目標 − 2 ms 未満なら遅めに、線形補間で再生位置を進める（ずれ 1 フレーム以内 ±2 %、超 ±5 %）。調整していない間は再生位置を整数サンプルに戻す（ビット一致の再生） |
| 欠落 | 後続フレームがあれば直前の実フレームを減衰させて補間（70 % → 35 % → 無音） |
| アンダーラン | データが尽きたら無音を出して再バッファリング |
| オーバーラン | バッファ量が最大遅延 + 1 フレームを超えたら、目標遅延まで古いフレームを読み飛ばす（ドロップ） |
| 時刻の飛び | 再生位置から容量以上先のフレームが届いたら内容を破棄して取り直す |

## 11. 既知の制限

- AUTH_FAIL は無認証のため、経路上の攻撃者（またはクライアントのポートを推測できる攻撃者）は
  偽の AUTH_FAIL で接続試行を中断させられる。経路上の攻撃者はパケット破棄で同等の妨害が可能なため許容する。
- 単一ユーザのみ対応（複数アカウントは今後の拡張）。
- サーバ起動ごとにソルトを再生成するため、クライアントは再起動後の初回接続時に鍵を再導出する。
- オーディオの Opus コーデックは未組み込み（インタフェースとコーデック ID のみ）。PCM16 は 1 方向あたり約 800 kbps を使う。
- サーバ・クライアントとも単一スレッドのイベントループで動作し、USB リセット中（最大 15 秒 × 方式数）は
  ループが停止する（その間にセッションが Keepalive 途絶で終了しうるが、クライアントは自動再接続する）。
